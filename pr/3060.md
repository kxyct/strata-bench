STRATA_RAM_ADAPT: copy an incoming expert out of its stage buffer instead of a second file read

## Title
STRATA_RAM_ADAPT: copy an incoming expert out of its stage buffer instead of a second file read

Issue: follow-up to #1837 / #1838 (in main as d7298883)

## Summary
On #1838 you measured no gain on the bench and a decode loss. We reproduced it on the `strata_bench.py` normal suite
(short chat −3.4% with `STRATA_RAM_ADAPT=8`). The option only pays off once the RAM copy has followed a conversation
for a while, and every move cost a file re-read on the decode thread (~0.77 ms, 8 moves per window), so a short
request ended before the moves paid back.

This change makes a move a memcpy out of the stage buffer the demand read just filled (~0.1 ms). Result: the short
bench no longer loses (+3.2% decode, prefill unchanged), and the long sessions this option is for gain clearly:
**+33.8% decode on 120 ShareGPT requests** and +19.2% on a 47-request session, with cumulative time down 23% / 13%.

## What changed
- `src/core/expert_source.cpp`, `include/strata/core/expert_source.hpp`: `replace_resident_staged()` moves a pair when
  the incoming blob is still in a finished stage buffer; the buffer is held under `stage_mu_` during the copy; same
  Foresight hold and between-window checks as `replace_resident()`. Counter `ram_staged()`.
- `src/program/generate.cpp`: the `STRATA_RAM_ADAPT` loop tries the staged copy first for every ranked pair (up to one
  per layer per window); `STRATA_RAM_ADAPT=<n>` now caps only the pairs that still need a file read (1 is enough).
  Pair selection, thresholds and the stage buffers' size and reuse are unchanged; still opt-in. The stats line counts
  staged moves.
- `tests/core/file_expert_source_test.cpp`: a staged move writes the exact bytes, refuses an unstaged or invalid pair
  and leaves the other experts untouched (pinned and pageable).
- `docs/DETAILS.md`: the `STRATA_RAM_ADAPT` entry.

## Extra Notes
v0.1.45 + this commit, RTX 3060 12 GB, IQ2_XS, 3769 VRAM expert slots, `--resident-budget-gib 20.5` (~74% of the
experts outside the GPU), NVMe. Fresh process per run, `STRATA_RAM_ADAPT=1`.

| Workload | Decode tok/s<br>OFF → ON | Prefill tok/s<br>OFF → ON | SSD expert reads / token<br>OFF → ON |
| --- | --- | --- | --- |
| `strata_bench.py` normal suite (15 req., short) | 38.7 → 39.9 (+3.2%, no loss) | 446 → 445 (−0.2%) | 15.9 → 9.7 (−39%) |
| ShareGPT, 30 conversations × 4 turns (120 req.) | 36.6 → 48.9 (**+33.8%**) | 119 → 142 (+19%) | 22.9 → 4.5 (−80%) |
| English 47-request session (in the kit) | 43.7 → 52.1 (**+19.2%**) | 277 → 292 (+5%) | 12.6 → 0.9 (−93%) |

Runs were OFF, ON, OFF; OFF in the table is the run after ON. The OFF run before ON gave 38.3 / 36.5 / 44.1 decode
tok/s, within 1% of the one after.

![ShareGPT 120 requests: decode ms per token, SSD expert reads per token and cumulative time saved, OFF vs STRATA_RAM_ADAPT=1](https://raw.githubusercontent.com/SanghunYun/Strata/ram-adapt-replay/charts/sharegpt120.png)

In the long session ON is faster from the first requests and stays there; the cumulative saving grows to 9% after 10
requests, 16% after 30 and 23% after 120. Paired per-request decode-time ratio (ON / OFF): ShareGPT 0.747 (95% CI
0.734–0.761), English 0.839 (0.819–0.861). One run per arm. With a RAM budget below the experts outside the GPU the
#669 lend-region warning is printed in every run; that is the case this option is for.

Replay: requests, the ShareGPT builder, replay/summary scripts, the exact engine arguments and our per-request numbers
are at https://github.com/SanghunYun/Strata/tree/ram-adapt-replay

Tests: CUDA sm86 Release `file_expert_source_test --rotation-gpu` passes with the new case. HIP gfx1100 Release
(ROCm 7.10): engine and test build and link, host-side `file_expert_source_test` passes; no AMD GPU inference.
